# 第一部分：先建立全景

## 1.1 这个项目是什么

一句话：**一个让用户"输入一句话梗概、得到一份可拍摄的分镜脚本"的网站。**

```
你在网页上：
  1. 注册账号、登录
  2. 创建一部短剧（如《雨夜便利店》）
  3. 给它加一集
  4. 点"AI 生成分镜"，填写镜头数（比如 6 个）
  5. 几秒后看到一张表：每个镜头的景别、运镜、画面描述、台词、时长
```

表面上看就这么简单。但为了让它**真的能工作、能上线、能给别人用**，
背后要做的事情比"调用一下大模型"多得多 —— 那些事情就是这份文档要讲的。

## 1.2 一张图看懂整个系统

```
 ┌────────────┐      HTTP      ┌──────────────────────┐     SQL      ┌──────────┐
 │   浏览器    │ ─────────────→ │   后端（FastAPI）      │ ──────────→ │  数据库   │
 │ (React 界面)│ ←───────────── │  Python 写的服务       │ ←────────── │ SQLite/   │
 └────────────┘     JSON       └──────────┬───────────┘             │ MySQL    │
                                          │ 异步任务队列（进程内）       └──────────┘
                                          ↓
                                   ┌──────────────────┐
                                   │ 大模型（DeepSeek │
                                   │  / 通义 / Mock） │
                                   └──────────────────┘
```

三个角色的分工：

| 角色 | 干什么 | 用什么技术 |
|---|---|---|
| **前端** | 用户看得见、点的界面 | React + TypeScript |
| **后端** | 看不见的"大脑"：算、存、管权限 | Python + FastAPI |
| **数据库** | 关机也不丢的数据 | SQLite（开发）/ MySQL（生产） |
| **大模型** | 真正"写剧本"的 AI | 任何 OpenAI 兼容接口 |

## 1.3 我们踩过的三个"新手必踩"的坑（先给你打预防针）

1. **"我电脑上能跑，你电脑上不行"** —— 因为环境不一样。
   解法是**虚拟环境 + 锁版本 + Docker**（第 5、8 节）。
2. **"接口返回 200 但页面白屏"** —— 因为页面要的 JS 文件从国外 CDN 加载失败。
   解法是**把静态资源自己托管**（第 9 节，这是本项目真实踩过的坑）。
3. **"改了表结构，老数据报错"** —— 因为 `create_all` 只会建新表、不会改旧表。
   解法是**数据库迁移 Alembic**（第 6 节）。

# 第二部分：一个词一个词扫盲

> 如果你对这些词已经很熟，跳过这节。每个词就三行：是什么、为什么、在这项目里对应什么。

## 2.1 服务（Service）和脚本的区别

- **脚本**：运行 → 出结果 → 结束。你以前写的 Python 基本都是脚本。
- **服务**：启动后**一直运行**，等人来请求，处理完返回结果，继续等下一个。
- 为什么需要服务：用你程序的人不在你电脑旁边，他们通过网络来访问。
  程序跑完就退出，别人就找不到你。

## 2.2 HTTP：网络上一次"对话"的格式

一次 HTTP 请求 = 方法 + 路径 + 数据：

```
POST /api/v1/dramas          ← POST 是方法（创建），路径是"对哪个资源"
Content-Type: application/json

{"title": "雨夜便利店"}        ← 数据（JSON 格式）
```

| 方法 | 含义 | 项目里的例子 |
|---|---|---|
| GET | 读取 | 看短剧列表 |
| POST | 创建 | 新建短剧、登录 |
| PATCH | 修改一部分 | 改剧名 |
| DELETE | 删除 | 删剧 |

响应带一个**状态码**：200 成功、201 创建成功、202 已受理（还没做完）、
400/404/409/422 是"你（调用方）的问题"、500/502 是"我（服务端）的问题"。

> 记忆法：**4 开头找自己，5 开头找服务端。**

## 2.3 API 和 JSON

- **API**：我给你开的一扇"窗"。你按我规定的格式发请求，就能用我的功能。
  我们所有窗口都在 `/api/v1/...` 下面，`/docs` 页面有完整清单。
- **JSON**：跨语言的数据格式，长得像 Python 的字典/列表。Java、JS、Go 都能读。

## 2.4 数据库：为什么不能存变量里

三个理由：**重启就没了**、多个服务进程**互相看不到**、**没法高效查询**。
数据库是专门负责"把数据可靠存到磁盘 + 快速查询"的程序。

基本概念：表（像 Excel 表）、行（一条记录）、列（一个字段）、
主键（唯一标识一行的 id）、外键（指向别的表的主键，建立关联）。

**ORM**：把"表"映射成"类"的技术。写 `db.get(Drama, 1)` 而不是手写 SQL 字符串，
好处是编辑器能自动补全、能报错，还能防 SQL 注入。

## 2.5 前端 vs 后端 vs 部署

- **前端**：浏览器里跑的代码，负责界面。它不会算业务，只会调 API。
- **后端**：服务器上跑的代码，负责"算得对、存得住、管得严"。
- **部署**：把代码放到一台 24 小时开机的服务器上，让全世界能访问。

## 2.6 Git：不是"备份"，是"时间机器"

每次 `git commit` 保存一个快照，可以回到任何历史版本。
**GitHub 上的提交历史就是你的工程履历** —— 面试官会看。

## 3.2 从一句话梗概到能播的短片（完整流水线）

这是整个产品最值得讲的地方 —— **一条从文字到成片的流水线**：

```
① 一句话梗概（人写的，十几个字）
      ↓ 大模型（DeepSeek）
② 分镜脚本：景别 / 运镜 / 画面描述 / 台词 / 时长 / 英文图像提示词
      ↓ 大模型（读剧本整理人物）+ 人工可改
③ 角色卡：性别 / 年龄 / 外貌 / 职业 / 背景 → 三视图（设定图，确认长相）
      ↓ 角色外貌文字（look_prompt，每张图都带）
④ 每个镜头一张画面
      ↓ 图生视频模型（可选，但决定了画面动不动）
⑤ 每个镜头一段会动的短片
      ↓ 台词解析 + 角色表 + 情绪分析
⑥ 每句台词 → 各自角色的音色与语速 → 拼成整个镜头的声音
      ↓ ffmpeg（本地，不花钱）
⑦ 竖屏 MP4：动态片段 + 配音按时长拼起来 —— 能直接播放的成片
```

注意 ③ 的位置是刻意的：**角色要在"批量画整集"之前确认好**。
否则等你花完 6 张图的预算，才发现角色长得不对，就得整集重画。

**关键点**：每一步的产出都是下一步的输入，而每一步都可以**独立失败、独立重试**。
这就是为什么每个环节都有自己的一张"任务流水"和自己的 `error` 字段 ——
视频合成失败不会让你重新花钱生成分镜。

**另一个关键点：每一步都是"可选的"，缺了就降级而不是崩掉。**
没有动态片段 → 用静态图合成；没有配音 → 补静音轨；角色表没分析出来 → 用默认音色。
一条流水线上有六七个外部依赖，**任何一环都不能让整条链路失效**。

## 3.3 一次"生成分镜"背后发生了什么（先看全局，细节在第四部分）

```
① 你点"AI 生成分镜"
② 浏览器 POST /api/v1/episodes/1/generate（带登录令牌）
③ 后端验证：登录了吗？这部剧集是你的吗？今天额度用完了吗？
④ 后端登记一个"任务"（状态=pending），回复 202 + 任务号  ← 只用了 48ms
⑤ 后端在后台真的去调大模型（这一步要几十秒，但你已经不用等了）
⑥ 浏览器每 0.8 秒问一次"任务好了吗？"（轮询 GET /tasks/{id}）
⑦ 模型返回文本 → 清洗解析 → 删除旧镜头、写入 6 个新镜头 → 任务状态=succeeded
⑧ 浏览器拿到"完成"，刷新出分镜表
```

**第 ④ 步是关键**：HTTP 连接只活了 48 毫秒，而不是挂着等大模型几十秒。
这就是"异步任务"——第四部分第 5 节细讲。

# 第四部分：十一个核心机制，逐个从零讲

## 4.1 鉴权：怎么知道"你是谁"

**最基础的问题**：服务器记不住人。每次请求都是独立的一次连接，
服务器怎么知道这次请求是"张三"发的，还是"冒充张三的人"发的？

**方案：登录发一张"令牌"（JWT）**

```
登录： 用户名+密码  ──验证──→  返回一张令牌（一串乱码）
以后： 每次请求都带着令牌 → 服务器验证签名 → 知道你是谁
```

令牌不是普通乱码，它是**三段 Base64 拼起来的（JWT）**：

```
eyJhbGci...（头：签名算法）.eyJzdWI...（体：用户id+过期时间）.签名
```

关键点：**任何人可以"看到"体里的内容（它只是编码，不是加密），
但改不了—— 一改签名就对不上，服务器会拒绝。**
所以"不要把密码等敏感信息放进令牌"，也正因为如此令牌有**过期时间**（我们默认 24 小时）。

**第二个问题：密码存在数据库里，泄露了怎么办？**

答案是**永远不存明文，存"哈希"**：

```
存的是：bcrypt("pw12345678") = $2b$12$...一串不可逆的摘要
验证时：把用户输入再哈希一次，和存的比对，一样就算对
```

为什么用 bcrypt 而不是 md5？因为 md5 算得**太快**了 ——
攻击者拿到哈希后可以每秒试几亿个密码。bcrypt 故意把每次验证做到约 100ms，
暴力破解的成本被抬高几个数量级。

**第三个问题：每个人只能动自己的数据**

我们的短剧表里有个 `owner_id` 字段，所有查询都带上"必须是当前用户"。
而且：**访问别人的资源返回 404（假装不存在），而不是 403（明说"这不是你的"）** ——
返回 403 等于告诉攻击者"这个 id 是真实存在的"。

> 面试话术：*"我做了 JWT 登录 + bcrypt 密码哈希 + 资源归属校验，
> 而且别人的资源统一返回 404 而不是 403，避免泄露资源存在性。"*

## 4.2 数据库迁移：表结构怎么安全地"进化"

**场景**：上线后你给 `shots` 表加了个字段 `audio_prompt`（配音提示词）。
怎么让**生产数据库**也加上这个字段，还不弄丢老数据？

- ❌ 手写 SQL 去线上执行：改错了没法回滚，而且"我改了什么"没有记录。
- ❌ `create_all`：它**只会建新表，不会给已有的表加列**，线上等着报"Unknown column"。
- ✅ **Alembic**：每次改表结构，生成一个**迁移脚本**（就是一段 Python），
  按顺序执行。特点：能 review（别人先审）、能回滚（`downgrade -1`）、
  能记录历史（谁、什么时候、改了什么）。

我们的迁移历史（`backend/alembic/versions/`）：

```
6e3ce928223b  初始四张表
0458c1af11b7  给 shots 加 audio_prompt 列
f6aa5ad7d285  加 generation_logs（调用流水）表
2c197a8b7f02  加 generation_tasks（异步任务）表
```

命令速记：`revision --autogenerate` 生成 → `upgrade head` 执行 → `check` 校验。

> 真实教训：autogenerate 生成的"加 NOT NULL 列"脚本，如果表里已有数据会执行失败，
> 必须手动补默认值。**自动生成的迁移一定要人工 review。**

## 4.3 配额与限流：AI 应用的钱袋子

**传统 Web 应用被刷接口**：浪费一点 CPU，自己会恢复。
**AI 应用被刷接口**：每次调用大模型都按量计费 —— **刷的是你的钱包**。

所以这个项目有两道防线：

**① 每日生成配额**（按用户，落库统计）
- 配置项 `DAILY_GENERATION_LIMIT`（默认 20 次/天）
- 每次生成前查"今天这个用户已经用了几次"，超了返回 429
- **失败的调用也消耗额度** —— 因为失败请求一样要付钱给模型厂商
- 每次调用记一条流水（`generation_logs` 表）：谁、哪一集、哪家模型、成功/失败。
  月底对账单时，你能说得清每一分钱花在哪。

**② 登录防爆破限流**（按用户名+IP，内存滑动窗口）
- 防止攻击者拿字典穷举密码
- "滑动窗口"：最近 N 秒内失败超过 M 次就暂时拒绝
- 诚实限制：计数存在内存里，重启清零、多实例各算各的 ——
  **生产环境要换成 Redis**（这些限制写在代码注释里了）

> 面试话术：*"AI 应用和传统应用最大的不同之一：传统应用防刷是防资源耗尽，
> AI 应用防刷是防直接的经济损失。我做了每日配额 + 调用流水 + 失败也计费。"*

## 4.4 大模型的"抽象"：为什么有个 MockProvider

我们的业务代码不直接 `import openai`，而是依赖一个**接口** `LLMProvider`：

```python
class LLMProvider(ABC):
    async def complete(self, *, system: str, user: str) -> str: ...
```

它有两个实现：

| 实现 | 是什么 | 用途 |
|---|---|---|
| MockProvider | 返回写死的假分镜，不联网不花钱 | 开发调试 + **跑测试** |
| OpenAICompatProvider | 真的调 DeepSeek/通义/Kimi/Ollama | 生产环境 |

好处：
1. **测试不依赖外部服务**：不联网、不花钱、不会因为模型随机性而"随机挂"。
   会随机失败的测试，三天内团队就会开始忽略它 —— 那还不如不写。
2. **换模型改三行配置**：`LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`。
3. **AI 的输出是"概率性"的**：你要求"只输出 JSON"，它还是可能给你包一层
   ```` ```json ````。所以解析必须容错，解析失败返回 502 而不是崩栈，
   并且**有专门一条测试**验证这个分支。

## 4.5 异步任务：为什么接口 48 毫秒就返回了

**同步做法的问题**：用户点"生成"，HTTP 连接就挂着等大模型 ——
几十秒里这条连接占着一个线程、一个浏览器请求，还可能超时。10 个人同时点，服务器要开 10 条"长线电话"。

**异步做法**：

```
POST /generate  →  202 + {"id": 任务号, "status": "pending"}   （立刻返回）
后台             →  执行：调模型 → 写库 → 状态改为 succeeded/failed
前端             →  每 0.8 秒 GET /tasks/{id} 轮询状态
```

这就是"任务队列"思想的最简形态。我们用的是 FastAPI 自带的 BackgroundTasks
（进程内后台执行）。**诚实的局限**：服务重启，没跑完的任务会丢；
多实例部署时任务只在其中一个实例跑。生产级方案是消息队列（Celery/arq + Redis），
但我们这套**状态机、轮询接口、幂等语义**和生产方案一致 —— 换队列时代码结构不用变。

> 注意一个细节：后台任务**不能复用请求的数据库会话**（请求结束会话就关了），
> 必须自己开新会话。这是异步任务最常见的 bug 来源。

## 4.6 测试：为什么有 188 个用例，以及它们守护什么

**测试的哲学**：把"手动点一遍验证没坏"这件事交给机器，1 秒跑完。

我们的做法：**每个测试用例一个全新的临时数据库**（跑完自动删），
通过"依赖覆盖"把真实数据库换成临时的。所以你本机**不用装 MySQL 也能跑测试**。

测试清单及它们守护的东西：

| 文件 | 守护什么 |
|---|---|
| test_auth.py | 注册/登录/令牌、**防用户名枚举**、**登录限流** |
| test_dramas.py | 增删改查、分页、**用户 B 碰不到用户 A 的数据** |
| test_synopsis.py | 用户写的大纲不被模型覆盖、AI 起草大纲时的**前情上下文**、配额 |
| test_generation.py | 异步任务全流程、**幂等**（重复生成不翻倍）、**坏模型返回 502→任务 failed** |
| test_images.py | 文生图全流程、**图片带鉴权才能读**、**单张失败不影响其它**、图片格式按文件头判断、删剧清理文件 |
| test_image_provider.py | 真实文生图适配器的**契约**（用本地假厂商）：请求格式、3 种返回结构、错误映射 |
| test_dialogue.py | **台词解析**：角色名被正确摘掉、括号提示识别、多角色分行、各种边界 |
| test_voice_profile.py | **音色矩阵**：性别/年龄 → 音色+音高+语速；语速映射的边界与夹取 |
| test_dubbing.py | **多角色配音**：角色名绝不进 TTS、男女角色音色不同、情绪改变语速、裸台词靠上下文推断说话人 |
| test_character_card.py | **角色卡**：年龄→年龄段联动、外貌提示词只含画面信息、**出场角色识别**（台词+名字并集）、旁白被排除、三视图跳过旁白、镜头编辑后**派生音频作废**、参考图只在单人镜头才传 |
| test_tts.py | 配音全流程、**只给有台词的镜头配音**、音频统一为 WAV、鉴权 |
| test_tts_provider.py | 真实配音适配器的**契约**：二进制/URL/base64 三种返回、逐句音色与语速 |
| test_clips.py | **图生视频**：用像素级断言证明"画面真的在动"、四种运镜、素材优先级、4xx 立刻失败、配额、鉴权 |
| test_video.py | 视频合成全流程（真跑 ffmpeg）、**没有画面就明确报错**、成片可播放性、鉴权 |
| test_task_recovery.py | **服务重启后把卡住的"假进行中"任务标记为失败**（否则前端一直转圈） |
| test_quota.py | 每日限额、**失败也消耗额度**、配额按用户隔离 |
| test_health.py | 健康检查、**文档不依赖境外 CDN**（白屏坑的回归测试） |
| test_migrations.py | **迁移能从零建库**、模型与库零差异 |

**这里有个很值得学的技巧：`test_image_provider.py` / `test_tts_provider.py` / `test_clips.py` 里的"假厂商"**。

真实厂商要花钱、要联网、还可能限流，不适合放进 CI。
但如果完全不管适配器，等接上真 Key 才发现"请求格式不对"就太晚了。
所以我们**用一个本地 HTTP 服务模拟厂商**，把"请求打到哪、带了什么头、body 里有哪些字段、
几种返回结构能不能解析、报错会不会被正确映射"全部固定成测试。

**剩下唯一的未知量就只有"真厂商的实际行为"** —— 那确实需要一次人工验证。
这是"在不可控的依赖面前，把可控的部分全部锁死"的工程思路。

### 一个"用测试代替耳朵/眼睛"的例子（很值得学）

图生视频这块有个特殊难题：**怎么自动断言"画面真的在动"？** 肉眼看不现实（CI 里没人看）。

我们的做法是 **像素级比对**：抽片段的**首帧**和**末帧**，逐像素算差异，
用"平均绝对差 + 变化超过阈值的像素占比"量化运动量。实测数据：

| | 平均差/255 | 明显变化像素 |
|---|---|---|
| 静态图（改造前） | 0.01 | **0.0%** |
| 接入动态片段后 | 25 ~ 40 | **45% ~ 64%** |

于是测试可以写成"运镜版必须 >20%，静止版必须 <1%"——**客观、可复现、给 CI 跑**。

> 这里还踩了一个很有意思的坑：测试图一开始用**棋盘格**，结果**平移运镜几乎测不出来** ——
> 因为周期图案平移一个周期就"看起来一样"；换成渐变又对缩放不敏感（平滑区域色差不到阈值）。
> 最后用**固定种子的随机噪声图**才对任何位移都敏感。

其中 `test_migrations.py` 是整个套件里最慢但最值钱的一类：
它保证"新同事克隆代码后能一键把数据库建出来"。

## 4.7 文生图 / 配音 / 视频合成：同一套抽象，连用四次

这三个功能看起来完全不同（一个出图、一个出声音、一个出视频），
但它们的**架构骨架是一模一样的** —— 每个都问同样三个问题：

| 问题 | 答案 |
|---|---|
| 调谁？ | 一个**接口**（Provider），不是具体厂商 |
| 产出什么？ | 一堆字节（图片/音频/视频），不是 URL |
| 存哪？ | 自己的磁盘，数据库里只存**相对路径** |
| 怎么给前端？ | 带鉴权的接口 + 前端的 blob URL |

具体展开：

| 模态 | 接口 | Provider 抽象 | Mock 怎么模拟 | 存哪 | 前端怎么用 |
|---|---|---|---|---|---|
| 图片 | `/images/generations` | `ImageProvider` | Pillow 画一张**写着提示词的占位图** | `media/shots/{id}.png` | `AuthMedia kind="image"` |
| 配音 | `/audio/speech` | `TtsProvider` | 标准库合成一段**真的能播放的 WAV** | `media/audio/shots/{id}.wav` | `AuthMedia kind="audio"` |
| 视频 | 本地 ffmpeg | （不需要 Provider） | —— | `media/videos/episodes/{id}.mp4` | `AuthMedia kind="video"` |

**为什么 Mock 也要产出"真的能用"的文件**（而不是空文件或假字节）：
因为"这张图能不能显示、这段音频能不能播放"**正是这条链路最容易出问题的地方**。
空文件验证不了 Content-Type 对不对、扩展名对不对、采样率合不合法 ——
而那恰恰是上线时才会暴露、且最难查的一类问题。

### 这一层里最值钱的三个设计

**① 图片不能存厂商给的 URL**

厂商返回的图片地址通常是**临时链接**（几小时就失效）。如果直接把 URL 存进数据库，
用户第二天回来就看不到图了。所以我们的原则是：**URL 用完即弃，图片下载到自己磁盘**。
（生产环境把存盘换成 OSS/S3 即可 —— 这正是 `media.py` 这一层存在的意义。）

**② 用户生成的媒体不能挂静态目录**

静态目录（`/media/xxx.png`）**没有鉴权** —— 谁猜到 URL 谁就能看到别人的图。
所以媒体必须走"登录 + 归属校验"的接口。

但这带来一个前端难题：**浏览器发 `<img>` / `<audio>` / `<video>` 请求时不会带 Authorization 头**。
解法是 `AuthMedia` 组件：用 `fetch` 带 token 取回二进制 → 转成 **blob URL** → 再交给标签显示，
并在卸载时 `revokeObjectURL` 释放内存。**安全要求推着前端架构走** —— 这是很典型的一例。

**③ 视频合成必须是「同步函数」，不能是 async**

ffmpeg 是**外部进程 + 阻塞等待**。如果写成 `async def`，它会卡住事件循环，把整个服务拖死。
写成普通 `def` 后，Starlette 会自动把它丢进线程池 —— 这才是正确做法。
（图片/配音任务之所以是 `async`，是因为它们在等网络 IO，性质完全不同。）

> **一句话总结**：一个抽象用一次可能是巧合，**连用四次就说明它是对的**。
> 这套 `Provider 接口 + Mock 实现 + 工厂 + 配置开关`，从文本复制到图片、配音、视频，
> 每次都是"加一个新目录 + 改几行配置"，业务代码和接口层一行没动。

## 4.8 台词解析：为什么"角色名"不能被念出来

**先看一个真实的尴尬**：大模型按剧本格式写台词，长这样 ——

```
林晚：这……这是什么？
陈默：别出声。
```

如果**整行**丢给配音模型，观众会听到：**"林晚，这……这是什么？"** —— 把角色名也念出来了。
这是最典型的"能跑但完全不能用"。

所以要有一层**台词解析**：把「谁说的」和「说了什么」分开。

### 真实数据比想象的脏（这就是为什么规则要基于真数据）

我们不是凭空猜格式，而是**从数据库里捞出真实生成的台词**再写规则。实际出现过：

| 真实写法 | 要处理成 |
|---|---|
| `林晚：这……这是什么？` | 角色=林晚，**只读后半句** |
| `（内心独白）林晚：我什么都没做。` | 提示=内心独白，角色=林晚，只读台词 |
| `（来电显示）：林晚，你怎么知道我的名字？` | 角色=来电显示（括号里就是说话人） |
| `旁白：现在是深夜，凌晨三点十九分。` | 角色=旁白 |
| `他站在雨里，一句话也没说。` | 没有说话人，整行都读 |

**意外收获**：模型自己写的 `（内心独白）`、`（来电显示）`、`（低声）` 这些**括号本身就是免费的表演提示**，
所以解析时单独留下来，交给后面的情绪分析用。

### 三个必须处理的边界（都是会真出问题的地方）

1. **冒号前是一整句台词**时不能当人名切掉。
   比如 `他站在雨里想了很久很久一句话也没说：然后转身走了。` ——
   如果无脑按第一个冒号切，内容就丢了。规则：冒号前含句末标点、或超过 12 字，就不算说话人。
2. **`林晚：` 后面什么都没有**（模型截断）—— 这种行**没有可朗读的内容**，
   但如果照原样送去合成就会把"林晚"念出来，所以**直接丢掉**。
   > 宁可少一句，也不要出戏。
3. **没有说话人的裸台词** —— 这是最难的一类，下面 4.9 专门讲。

## 4.9 角色音色与情感：让每个人有自己的声音、语气跟着剧情走

这一步解决三个问题：**谁在说、用什么声音说、用什么语气说**。

### 问题一：角色表（谁是谁）

一个镜头里可能有好几个人说话。要让每个人有自己的声音，先得有一份"谁是谁"的档案：
性别、年龄段、说话风格。

**AI 打底 + 人工可改**：让大模型读剧名/梗概/大纲/台词样本，产出角色档案；
但它会猜错（名字看不出性别、年龄只能靠剧情推），所以结果是**存在数据库里、可编辑的数据**，不是写死的常量。

接口层面也刻意分开：`POST /dramas/{id}/cast/analyze` 单独一个接口，
让用户能在界面上**先过目改完，再去配音** —— 音色才不会错得离谱。

### 问题二：只有 1 个男声（硬限制，以及我怎么绕过去）

智谱 GLM-TTS 可用的音色只有 7 个。**我听不到音频**，没法靠耳朵判断哪个是男声。

于是我换了个办法 —— **测基频（F0）**。成年男声约 85~155Hz，女声约 165~255Hz。
用自相关算法算每个音色的基音周期，结果：

| 音色 | 基频 | 判断 |
|---|---|---|
| **xiaochen** | **134 Hz** | **男声** |
| tongtong / kazi | 183 Hz | 女声（偏低） |
| jam / chuichui / luodo | 238~247 Hz | 女声 |
| douji | 316 Hz | 童声感 |

**结论：能用的男声只有 1 个。** 但短剧里男性角色往往不止一个（年轻男主 + 中年反派 + 老年长辈）。

**解法：同一个音色做音高偏移。**
    变调由 ffmpeg 完成：`asetrate` 改变采样率（变调）→ `aresample` 还原 → `atempo` 反向补偿（保持时长）。
于是"年轻男 / 中年男 / 年老男"就有了区别，再叠一层语速（老年人说话本来就慢）：

| 角色 | 音色 | 音高偏移 | 语速 |
|---|---|---|---|
| 年轻男性 | xiaochen | +6% | 1.04 |
| 中年男性 | xiaochen | 0 | 0.98 |
| 年老男性 | xiaochen | −9% | 0.88 |
| 老年女性 | kazi | −7% | 0.88 |

> **这套映射是"可改的"，而且我在文档里明说：那些"年龄感"标签是我按基频推的，真实听感只有耳朵能判断。**
> 所以前端可以改、接口可以改 —— 而不是写死在代码里。

### 问题三：语气怎么跟着剧情走（这里有个"看起来能用但其实不能用"的坑）

智谱文档的官方示例是这样写的：`开心：拆开快递…`、`悲伤：我养了三年的花枯萎了…`，
看起来就像"把情感写在文本里当指令"。

**我实测后发现不行。** 验证方法很巧：把生成的音频**再送去语音转文字**，看情感词有没有出现在转写结果里 ——
**这不需要耳朵，是客观判据**：

| 输入 | 转写结果 |
|---|---|
| `我什么都没做。` | `我什么都没做` ✅ |
| `急迫：我什么都没做。` | **`急迫，我什么都没做`** ❌ 被念出来了 |
| `（急迫）我什么都没做。` | **`急迫我什么都没做`** ❌ |
| `[急迫]我什么都没做。` | **`急迫我什么都没做`** ❌ |

**任何形式的情感标签都会被读出来。** 所以语气只能用**真实可控的参数**：

| 手段 | 怎么用 |
|---|---|
| **语速** | 急迫/愤怒调快，悲伤/暧昧调慢（实测 1.5 倍→2.61s，0.7 倍→3.47s，确实有效） |
| **音色 + 变调** | 见上面的矩阵 |
| **台词本身的标点** | `……`、`？` 会自然带出犹豫感（不改字，只靠原文） |
| **模型自身的情感推断** | GLM-TTS 会"根据上下文智能预判文本情绪" —— 这部分免费得到 |

**语速映射里有个细节值得看**：强度**只放大"偏离 1.0 的部分"**：

```
最终语速 = 角色基础语速 × (1 + (情绪系数 - 1) × 强度放大)
```

强度 0.5（一般）时几乎不改变语速；强度拉满才明显加快或放慢。
否则只要标了情绪就一律加速，**整集听起来会很赶、很假**。

### 问题四：没有说话人的裸台词怎么办

这是真实踩到的 bug：大模型有时会生成**不带"角色名："前缀**的台词，比如单独一行 `我找了你好久。`

当时的代码把"没写说话人"的句子**一律当旁白处理** —— 而旁白是女性音色。
结果：从剧情看明明是男主说的话，出来是女声。

三层修复：
1. **治本**：分镜提示词里加铁律 —— 每句台词必须写「角色名：」，绝不允许只写台词；
2. **上下文推断**：情绪分析那步让大模型**结合剧情判断**裸台词是谁在说（它能看见整集大纲、镜头描述、角色性格）；
3. **兜底**：还推断不出来就延续同一镜头里上一句的说话人；括号写"旁白/画外音"的才归旁白。

回归测试就一句话：**"男主台词必须配男声"**。

### 逐句合成 + 拼接

一个镜头里两个人对话，就要**逐句用各自的音色和语速合成**，再拼成这个镜头的声音。
拼接用 ffmpeg 的 concat 滤镜（会重采样对齐，所以各段格式不同也能拼），句间插一小段静音。

**为什么逐句落盘而不是整段一次合成**：某一句失败只要重做那一句，不用整段重来。
数据库里因此多了一张 `dialogue_lines` 表（一句一行，记录说话人/情绪/语速/音频路径/失败原因）。

## 4.10 图生视频：从"图片幻灯片"到"真的会动"

### 先说清楚"改造前"到底是什么

最初的合成用的是：

```python
args = [exe, "-y", "-loop", "1", "-i", str(image)]   # -loop 1 = 一张图无限循环
```

配 `-shortest` 让片段长度跟着配音走，最后把每个镜头拼起来 ——
**画面完全静止，只有声音在动**，本质是"配音 PPT"。这一步是刻意留的口子：
接口设计成"每个镜头一段素材，然后拼接"，就是为了将来把"图片"换成"真视频"时只改一处。

### 图生视频（i2v）是什么

**给一张静图 + 一句"接下来怎么动"的描述，生成一段真的会动的短片。**
它和"给个提示词凭空画图"（文生图）是两件事。

### 第四个模态：VideoClipProvider

照抄文本/图片/配音那一套（接口 + Mock + 工厂 + 配置开关），这次特别的是：

| 模式 | 是什么 | 成本 |
|---|---|---|
| `none` | 不生成动态片段，退回静态图（也就是最初的行为） | 0 |
| `mock` | **本地 ffmpeg 做运镜**（推近/拉远/左右平移） | **0，且不联网** |
| `openai_compat` | 真调图生视频模型（智谱 CogVideoX 等） | 0.5~1 元/次 |

**mock 的巧思**：它产出的**不是占位符，而是一段真实可播放、真的会动的视频**（只是"动"的方式是运镜，
不是人物真做动作）。这样：
① 没有视频模型 Key 也能把「动态片段 → 合成」整条链路跑通、测通；
② 真实 i2v 失败或太贵时可以退回它；
③ 成本敏感的场景可以直接当正式方案。

### 向后兼容：有片段用片段，没有就退回静图

```python
def shot_source(shot):
    if shot.clip_path and 文件存在:  return 片段, True    # 优先用动态片段
    if shot.image_path and 文件存在: return 图片, False   # 退回静态图
    return None, False
```

这十几行是"**可选功能不能让人没法用**"的典型：没接 i2v、或某个镜头生成失败，
成片照样能出，只是那一格是静图 —— 而不是整个功能报错。

### 异步套异步（两层轮询）

图生视频很慢（几十秒到几分钟），厂商一律做成异步接口。而我们自己那套"任务表 + 轮询"也是异步，
所以变成两层：

```
我们的任务表(pending→running→succeeded)   ← 前端轮询 /tasks/{id} 看这个
      └── 后台任务内部：POST 提交拿 id → 循环 GET 查结果 → 下载 → 落盘
```

**结构上和自己那套完全同款** —— 区别只是我们要在后台任务内部再轮询一次厂商。

### 两个把我坑惨的 ffmpeg / HTTP 问题（很值得记）

**① `-stream_loop -1` 配 `-shortest` 不收敛**

动态片段可能比台词短，我的想法是"循环播放它，靠 `-shortest` 在语音结束时自动停下"。
逻辑上说得通，**实际上不会停**：实测一个镜头编了 **15 分钟**还在烧 CPU（CPU 时间 887 秒、内存 811MB）。

**修法**：**显式算出时长并用 `-t` 限长**（音频多长就编多长）。

| | 耗时 |
|---|---|
| 修复前 | 单段 **> 900 秒**（还没停） |
| 修复后 | **6 段共 3.3 秒** |

> **教训**：**"让程序自己停"永远不如"明确告诉它停"**。
> 尤其是 ffmpeg 这类工具，`-shortest` 这种"自动推断"的选项在边界情况下很不可靠。

**② 轮询遇到 4xx 不能当网络抖动**

有个镜头的任务，轮询厂商接口一直返回 **400 Bad Request**。我的代码把它当成"网络抖动"**继续重试**，
于是白等了 900 秒才超时 —— 用户看到的就是"卡住了"，排查也没线索。

**修法**：区分错误类型 —— **4xx 是永久性错误（任务失效），立刻失败**；只有 5xx 和真正的网络异常才重试。
顺手把默认轮询超时从 900 秒降到 360 秒（5 秒的片段等超过 6 分钟就是有问题）。
并且把**异常类型**也写进错误信息（原来只写"失败"，等于没说）。

**③ 顺带一个媒体处理常识**：接入 AI 视频后，`-map` 显式指定轨道变成必需 ——
有些模型会给视频带一条音轨，不指定的话 ffmpeg 会挑错轨道，或拼出两条音轨。

## 4.11 角色卡与三视图：让同一个角色在每张图里长得像

这是整个项目里**最需要"想清楚它到底能做什么"**的一个功能。

### 问题：模型没有记忆

文生图模型每次调用都是**全新的生成**。所以同一部剧里，第 1 个镜头和第 6 个镜头里的"苏晚"
可能是两个完全不同的人 —— 在短剧里这是致命的，观众根本认不出谁是谁。

### 解法一（做到的）：把"这个人长什么样"固定成一段文字

角色卡把外貌描述存成数据，画每个镜头时**都把它拼到提示词最前面**：

```
【角色外貌（每张图都带）】；【剧集风格】；【这个镜头的场景】
   女性，26岁，地铁站夜班值班员，外貌：黑色齐肩短发、单眼皮、身形瘦小，穿深蓝色制服外套
```

**顺序是有讲究的**：角色在前、场景在后。模型对提示词前半段更敏感，
把"长什么样"放前面比放后面更容易画出同一个人。

这里有个设计细节：`look_prompt` **留空就自动从角色卡生成；填了就以它为准**。
这样用户既能享受"改完字段自动同步"的省省心，也能手写一段更精准的锚定
（比如"参考某位演员"）—— 而且手写的优先级必须高于自动生成，否则用户改一次就被覆盖一次。

### 解法二（做了一半的）：三视图

三视图 = 正面/侧面/背面并排的"角色设定图"。它有两个作用，但**只有一个真正成立**：

| 作用 | 成立吗 | 说明 |
|---|---|---|
| 给用户一个"这角色长这样"的确认物 | ✅ 成立 | 在画整集之前就能发现"角色不对"，省下整集画面预算 |
| 让模型"看着三视图"去画镜头 | ❌ **不成立** | 智谱的 cogview-3-flash / cogview-4 / glm-image **都是纯文本输入**，不接受参考图 |

**这一点我特意写进代码和文档里**，因为它直接决定了用户该期待什么：
三视图**不是**图像级的参考，长相一致性靠的还是那段文字（look_prompt）。
所以 `ImageProvider` 上留了一个 `supports_reference` 能力标志：
按模型名硬编码判断会随厂商更新失效，而显式的能力标志能让"不支持"这件事被正确降级并记日志。

> **顺带一个真实的能力探测结论**：智谱三个画图模型的官方文档"输入模态"一栏写的都是**文本**，
> 所以"参考图/角色参考"这条路在当前厂商下走不通。想真正锁住长相，必须换支持
> image-to-image 的厂商 —— 而我们的接口已经留好了位置，实现里改两行就能接。

### 旁白不是角色

一个容易忽略的问题：`旁白` 也在角色表里（因为配音要给它分配音色），
但它**没有形象**。所以：

- 生成三视图时**跳过**旁白（给它画一张"旁白的三视图"纯属浪费钱）；
- 画面提示词里**排除**旁白（否则会往提示词里塞一句毫无意义的"女性，青年"，白白稀释画面信息）。

### 镜头可以手动编辑，但"派生数据"要作废

AI 生成的分镜只是初稿。用户能改画面描述、台词、时长、图像提示词。

**这里最需要想清楚的是**：改了某个字段之后，之前生成的东西还算不算数？

| 改什么 | 派生数据怎么办 | 为什么 |
|---|---|---|
| `dialogue`（台词） | **全部作废**：删逐句台词行 + 删每句音频 + 删整段镜头音频 | 角色分配、情绪、语速、每句音频**全是从台词解析出来的**；台词变了配音就是错的 |
| `description` / `image_prompt` | **保留**旧图 | 那是花过钱的结果，删不删应该由用户决定（点「生成画面」才会覆盖） |

作废而不是"尝试修补"：修补要重跑角色分配和情绪分析（还得调模型花钱），
而且用户改台词通常意味着语气也变了，重做才是对的。
**作废时连磁盘上的音频文件一起删** —— 只删数据库行会留下永远没人引用的孤儿文件。

### 一个必须如实记录的工程结论：三视图排版是"抽奖"

我为了让模型稳定画出"三个全身视角 + 写实风"，连续试了五个版本的提示词，
每一版都真的跑了、看了生成结果：

| 版本 | 提示词变化 | 实际结果 |
|---|---|---|
| v1 | 三个视角一句话说完 | 三个全身视角 ✅ / 但成了**插画风** ❌ |
| v2 | 展开写"能看到脸""看到后脑与后背" | **头肩特写**，全身没了 ❌ |
| v3 | 画风前置 + 视角单独一行 + 禁止半身特写 | **拼贴画**，只出现一个侧身 ❌ |
| v4 | "写实摄影风格"打头 + 视角同一句 | 写实风 ✅ / 但**只画了一个人** ❌ |
| v5 | 三视角打头 + 画风塞括号 | **同一提示词跑两次**：一次写真单人、一次插画三视角 |

**结论：模型对"一张图里排三个视角"的版面控制本身就不稳定，继续调提示词只是在抽奖。**
所以产品上的解法不是"调到一次成功"，而是：

1. **给「重画三视图」按钮** —— 不满意就再抽一次（cogview-3-flash 免费，几乎零成本）；
2. **三视图只是确认物**，真正锁定长相的是 look_prompt 那段文字；
3. 把这段"抽奖记录"写进代码注释，避免以后有人（包括我自己）以为改措辞就能解决。

> 这是很少见但很值得讲的体验：**有些质量的瓶颈在模型，不在你的代码**。
> 成熟的工程判断是"识别出这一点，然后在产品层面给用户重试的能力"，而不是无止境地调参数。

# 第五部分：一次请求的完整旅程（最终版）

以"登录用户点击生成分镜"为例，把前面所有机制串起来：

```
① 浏览器：POST /api/v1/episodes/1/generate
   请求头带 Authorization: Bearer <JWT>
        │
② FastAPI 依赖链依次执行：
   ├─ 校验 JWT 签名+过期时间 → 得到"用户 id=7"   （4.1）
   ├─ 查剧集 1 存在且 owner_id=7，否则 404       （4.1）
   ├─ 配额检查：今天已用 3/20 次，还没超         （4.3）
   ├─ 记一条调用流水（pending，先占额度）         （4.3）
   └─ 创建任务行（status=pending）
        │
③ 返回 202 + 任务号，HTTP 连接结束（~48ms）      （4.5）
        │
④ 后台任务开始：
   ├─ 任务状态 → running
   ├─ 用自己的数据库会话，加载剧集和短剧信息
   ├─ 拼提示词：剧名+题材+梗概+本集大纲+镜头数
   ├─ await 大模型（Mock 即时返回 / 真实模型几十秒）（4.4）
   ├─ 容错解析 JSON（模型不听话就 502→failed）     （4.4）
   ├─ 删旧镜头 + 插新镜头（幂等）→ commit
   ├─ 任务 → succeeded，流水 → success
        │
⑤ 浏览器每 0.8 秒 GET /tasks/{id}：
   pending → running → succeeded → 自动刷新分镜表
```

任何一步抛异常，都被统一的错误处理器接住，返回同一种格式：

```json
{"error": {"code": "quota_exceeded", "message": "今日生成次数已达上限（20 次），明天再来吧"}}
```

前端只需要写一套错误解析逻辑（`frontend/src/api.ts` 里的 `ApiError`）。

# 第七部分：面试怎么讲（30 秒版 + 常见追问）

> "我做了一个 AI 短剧创作的全栈项目，核心是一条**从一句话梗概到竖屏成片的流水线**：
> 大模型写分镜 → 文生图出画面 → **图生视频让画面真的动起来** → 多角色情绪配音 → 本地 ffmpeg 合成 MP4。
> 用户注册登录后建短剧、加剧集，每一集可以自己写大纲、也能让 AI 依据前几集内容起草。
>
> 后端是 FastAPI + SQLAlchemy + Alembic，四个关键设计：
> 一是**把四种模态（文本/图片/配音/视频）都抽象成 Provider 接口**，各配一个 Mock 实现，
> 所以测试不联网不花钱、CI 不依赖外部 API —— 同一套抽象连用四次，说明它是对的；
> 二是**所有重活都做成异步任务**，202 + 状态轮询 + 进度，接口毫秒级返回；
> 三是**AI 调用按用途分别配额**（分镜/画面/动态镜头/配音/视频各有限额），并记录调用流水，
> 失败也计费 —— 因为失败请求一样要花钱；四是**媒体全部走带鉴权的接口**，
> 不做公开静态目录，别人的资源一律 404。
>
> 163 个测试用例全绿，其中真实厂商适配器用**本地假厂商服务**做了契约测试；
> 图生视频这块还用**像素级比对**自动断言"画面真的在动"（静态图 0% 像素变化，
> 接入动态片段后 45%~64%），让"有没有动"这件主观的事变成 CI 能跑的客观指标。
> 前端 Vite + React + TS，Docker + Nginx 部署，CI 里后端测试和前端构建都会跑。"

**准备好被追问**（答案都在本文档和 `docs/00` 里）：

- JWT 被篡改了怎么办？为什么令牌要有过期时间？
- bcrypt 和 md5 的区别？为什么密码不能明文存？
- 异步任务用什么实现？生产环境为什么换成消息队列？
- **为什么图片/音频/视频不能存厂商给的 URL？**（临时链接会失效）
- **为什么媒体不挂静态目录？那前端怎么显示需要鉴权的图片？**（blob URL）
- **为什么视频合成任务写成同步函数而不是 async？**（ffmpeg 阻塞会拖死事件循环）
- 幂等是什么意思？你的生成接口为什么是幂等的？
- `create_all` 和 Alembic 的区别？
- 4xx 和 5xx 的区别？别人的资源为什么返回 404 而不是 403？
- AI 应用和传统 Web 应用最大的不同是什么？（答案：上游是概率性的 + 每次调用是钱）

**关于多模态配音和视频，会被追问的这些**（这是项目里最新的部分，也是最能聊出深度的地方）：

- **大模型输出的台词里带了"角色名："，你怎么保证配音时不把角色名念出来？**
  （专门一层台词解析；而且规则是从**真实数据**里总结的，不是凭空猜格式）
- **你怎么让不同角色有不同声音？只有几个音色，男性角色不止一个怎么办？**
  （角色表 + 音色/音高/语速矩阵；男声只有一个，靠**音高偏移**派生年轻/中年/老年）
- **你项目里的情感标签是怎么生效的？能直接写进文本当指令吗？**
  （**实测不行** —— 用语音转文字反证：`急迫：我什么都没做` 会被读成"急迫，我什么都没做"；
  所以只能走语速/音色/变调这些真实可控的参数）
- **你听不到音频，怎么知道哪个音色是男声？**
  （测基频 F0：男声 85~155Hz、女声 165~255Hz；实测只有一个男声 xiaochen 134Hz）
- **"画面真的动了"这件事你怎么测的？**
  （像素级比对首末帧；另外踩过测试图选材的坑：棋盘格测不出平移、渐变测不出缩放）
- **为什么接视频模型不需要改动业务代码？**（第四个模态，同一套 Provider 抽象）
- **i2v 让视频变长变慢后，你踩了什么性能坑？**
  （`-stream_loop -1` + `-shortest` 不收敛，单段编了 15 分钟；改用显式 `-t` 后 6 段 3.3 秒）
- **厂商接口返回 4xx，你的重试策略是什么？**
  （4xx 立刻失败、5xx 和网络异常才重试 —— 原来一律重试导致白等 900 秒）
- **外部依赖这么多，某一环挂了怎么办？**
  （每步都降级：没动态片段用静图、没配音补静音、没角色表用默认音色）

# 附录二：踩坑合集（这些才是真正学到东西的地方）

按主题整理。**每一条都是真实发生过的**（不是网上抄的"常见问题"），
面试时讲这些比讲技术栈有说服力得多。

### 数据库与迁移

| 踩的坑 | 根因 | 教训 |
|---|---|---|
| 加了字段，启动报 `no such column` | 开发库是 `create_all` 建的，**只建表、不加列** | 表结构变更**只有迁移算数**；`create_all` 只适合建空库 |
| Alembic 自动生成的迁移**漏了 `server_default`** | autogenerate 不会为新 NOT NULL 列补默认值，而表里已有数据 | 有数据的表加非空列，必须手工补 `server_default`（这个坑踩了 3 次） |
| 生成了迁移但**忘了在开发库执行** → 接口 500 | 只跑了 `revision --autogenerate` | 新迁移必须 `alembic upgrade head`，而且要提醒自己"换库了就得跑" |
| 真实 MySQL 上才暴露的字符集/权限问题 | 开发一直用 SQLite | **上线前必须在真库上跑一遍**（我们确实换了真 MySQL 9.6 验证） |

### ORM 与会话（最阴的一类）

| 踩的坑 | 根因 | 教训 |
|---|---|---|
| 角色分配和情绪分析**被静默跳过**，所有台词同一个声音 | `selectinload` 已经把关系加载成**空集合**，后面再查**不会覆盖**已加载的关系 | ORM 的"缓存"是隐式的；批量任务里**显式查询**比依赖关系加载更可靠 |
| 语速永远覆盖角色的基础语速 | `DialogueLine.speed` 默认 `1.0`，而 `1.0` 是 **truthy** | 用 `None`（而不是 1.0）表达"还没设置"；**默认值不要选一个有意义的值** |
| 后台任务读不到请求改的数据 | 请求结束会话就关了 | 后台任务必须**自己开新会话** |

### AI 输出解析（概率性上游）

| 踩的坑 | 根因 | 教训 |
|---|---|---|
| 配音把"角色名"念出来了 | 整行台词丢给了 TTS | AI 的输出**必须解析成结构**再用；解析规则要**从真实数据里总结** |
| 男主的台词配成了女声 | 没写说话人的裸台词被一律当旁白（女性音色） | 三层修复：提示词约束 + 上下文推断 + 兜底延续上一句 |
| **情感标签被念出来**（"急迫，我什么都没做"） | 以为厂商文档的 `开心：文本` 是可用指令 | **用语音转文字反证**（客观判据）；语气只能走语速/音色/变调 |
| 模型返回的 JSON 不合法/被 ``` 包住 | 大模型输出是概率性的 | 容错解析 + 明确的失败信息 + **Mock 覆盖三种返回结构** |

### 媒体处理（ffmpeg）

| 踩的坑 | 根因 | 教训 |
|---|---|---|
| 图片是 JPEG 却按 PNG 返回 | 扩展名写死 `.png`，Content-Type 写死 `image/png` | **按文件头（magic bytes）判断格式**，别信扩展名 |
| **合成卡死 15 分钟**（CPU 烧了 887 秒） | `-stream_loop -1` 配 `-shortest` **不收敛** | **"让程序自己停"不如"明确告诉它停"**（显式 `-t`，6 段 3.3 秒） |
| 音频格式不统一拼不起来 | 各段采样率/声道不同 | concat 滤镜会重采样对齐；**统一输出格式**是更省心的做法 |
| 删短剧后磁盘留下一堆孤儿文件 | 只删了数据库记录 | 删除时**收集所有媒体路径一起删**（视频文件尤其大） |

### 网络与外部依赖

| 踩的坑 | 根因 | 教训 |
|---|---|---|
| 轮询遇到 4xx **傻等 900 秒** | 把永久性错误当成了网络抖动 | **4xx 立刻失败、5xx/网络异常才重试**；错误信息要带异常类型 |
| 免费视频模型一直 429 | 免费额度被挤爆 | 厂商限流是常态，错误信息要能让人看懂（"排队/限流"而不是"失败"） |
| 请求量太大被限流 | 没做客户端节流 | 配额按用户 + 按用途分别设限 |

### 测试与工程环境（最容易被忽略）

| 踩的坑 | 根因 | 教训 |
|---|---|---|
| 测试结果**依赖开发机的 `.env`** | conftest 没固定新加的配置项 | **所有外部能力都必须在测试里固定死**，测试不能读开发者的本地配置 |
| 棋盘格测试图**测不出平移运镜** | 周期图案平移一个周期"看起来一样" | 测试素材要选对；随机噪声图对任何位移都敏感 |
| 登录限流**形同虚设** | 限流器每次请求新建实例，计数攒不起来 | 进程内状态必须**做成单例**（`lru_cache`）—— 被测试抓出来的 |
| CI 突然变红 | `requirements.txt` 漏了新依赖（Pillow / imageio-ffmpeg） | 本地能跑不代表 CI 能跑；**依赖清单要跟着代码走** |
| PowerShell 写文件给 Python 加了 BOM | `Set-Content -Encoding UTF8` 会加 BOM | 用 `UTF8Encoding($false)`；BOM 会让 Python 报"非打印字符" |
| 控制台打印 `✓` 报 `UnicodeEncodeError` | Windows 控制台是 GBK 编码 | 脚本输出用 ASCII；**这类"环境噪音"别浪费时间调** |
| 排查进程时"看不到 ffmpeg" | 内置二进制的进程名是 `ffmpeg-win-x86_64-v7.1`，不是 `ffmpeg` | 排查时用**通配符**匹配进程名 |

> **一句话总结这些坑**：真正的工程能力，**大部分不是"写出来"的，而是"踩出来并被测试锁住"的**。
> 上面每一条，现在都对应一个测试用例 —— 这才叫"学到手了"。
