# 架构决策记录：为什么这么设计

> 这份文档回答的是面试官最爱问的那句话：**"你为什么这么写？"**
> 每一节的结构是：决策 → 理由 → 不这么做会怎样。

---

## 1. 为什么选 FastAPI，而不是 Django / Flask

**决策**：FastAPI。

**理由**：
- 异步原生。本项目大量时间花在等大模型响应（几十秒），
  异步在这段时间里可以处理别的请求，同步模型只能占着线程干等。
- 自动生成 OpenAPI 文档。`/docs` 页面是可交互的，前端联调不用写接口文档。
- Pydantic 校验内建。请求参数不合法时框架直接返回 422 并说明哪个字段错了，不用手写 if。
- 类型注解即文档，代码可读性高，对 AI 辅助编码也友好（模型更容易理解你的意图）。

**不这么做会怎样**：
- Django：自带 ORM/Admin/模板，功能全但重，异步支持是后加的，做纯 API 服务显得笨重；
- Flask：极简但校验、文档、异步都要自己拼装，一个项目下来大量时间花在选轮子上。

**什么时候该反过来选 Django**：需要后台管理系统、需要完整用户体系、团队已熟悉 Django。技术选型没有绝对对错，只有场景匹配。

## 2. 为什么分层（api / schemas / services / db / core）

**决策**：按职责分层，依赖方向单向向下：`api → services → db`。

**理由**：
- 接口层回答"怎么暴露"，服务层回答"业务怎么做"，数据层回答"怎么存"。
- 换 Web 框架只改 api 层；换数据库只改 db 层；换模型只改 services/llm。
- 最实际的好处：**服务层的逻辑可以被定时任务、CLI、消息消费者复用**，不用复制粘贴。

**不这么做会怎样**：所有逻辑堆在路由函数里，一个函数 300 行，
第一个月能跑，第三个月没人敢改，加需求就是加 if。

---

## 3. 为什么 Schema 和 ORM Model 要分开写

**决策**：`app/db/models.py`（数据库结构）与 `app/schemas/*.py`（对外契约）两套。

**理由**：
- 数据库字段和 API 字段天然不同。比如 `Shot` 表里没有"所属剧名"，
  但前端列表页可能需要；数据库里有 `created_at`，但某些接口不该暴露。
- 安全：如果直接用 ORM 模型当响应体，将来给表加一个 `password_hash` 字段，
  它会**自动出现在接口返回里**。这是很经典的越权泄露事故。
- 演进自由：表可以随便重构，只要 API 契约不变，前端就不受影响。

**不这么做会怎样**：改一个数据库字段，全公司前端跟着改。

---

## 4. 为什么要抽象出 LLMProvider（本项目的核心设计）

**决策**：业务代码依赖 `LLMProvider` 接口，不直接 `import openai`；并提供 `MockProvider`。

**理由**：
- **可测试**：测试用 `MockProvider`，不联网、不花钱、结果稳定。
  如果测试真的去调大模型，CI 会因为网络抖动随机失败，测试就失去了意义。
- **可替换**：DeepSeek / 通义 / Kimi / 本地 Ollama 都提供 OpenAI 兼容的
  `/chat/completions`，换模型只改 `.env` 里的三行，业务代码一行不动。
- **可降级**：模型服务挂了，可以临时切回 mock 或备用厂商，服务不至于全站不可用。

这是"依赖倒置原则（DIP）"的真实收益，不是为了设计模式而设计模式。

**不这么做会怎样**：模型 SDK 的调用散落在几十个函数里，
某天厂商改了 SDK 或你要换模型，全项目改一遍。

## 5. 为什么所有错误返回同一种 JSON 结构

**决策**：统一为 `{"error": {"code": "...", "message": "..."}}`，并通过异常处理器兜底。

**理由**：
- 前端只写一套错误处理逻辑，不用为每个接口猜格式。
- `code` 是给程序判断的（稳定不变），`message` 是给人看的（可以改文案），
  两者混在一起是常见设计缺陷。
- 未捕获异常也返回 500 JSON 而不是 HTML 堆栈：既不泄露内部结构，也不会让前端 JSON 解析直接崩。

**不这么做会怎样**：有的接口返回 `{"detail": ...}`，有的返回 `{"msg": ...}`，
有的直接返回 HTML 错误页，前端要写一堆兼容代码。

## 6. 为什么配置必须走环境变量

**决策**：所有可变项集中在 `Settings`，从环境变量 / `.env` 读取。

**理由**：
- 同一个 Docker 镜像应该能跑在开发、测试、生产三套环境上，**区别只是环境变量**。
  这是 12-Factor App 的第三条，也是"构建一次、到处运行"的前提。
- 密钥绝不进代码库。`.env` 写进 `.gitignore`，`.env.example` 提交上去告诉同事需要配什么。

**不这么做会怎样**：生产密钥被提交到 GitHub，
或者为每套环境打一个不同的镜像（进而"测试环境和生产不一致"的经典事故）。

---

## 7. 为什么开发用 SQLite、生产用 MySQL

**决策**：默认 `sqlite+pysqlite:///./ai_drama.db`，生产用 `mysql+pymysql://...`。

**理由**：
- SQLite 是单文件、零配置，`git clone` 完就能跑，新人上手成本接近 0。
- MySQL 是生产刚需：真正的高并发写入、多实例共享数据、备份和权限体系。
- 两者之间用 SQLAlchemy 抹平差异，**切换只需要改环境变量**——
  但要注意方言差异（见第 8 节的两个坑）。

**必须注意的差异**：
1. SQLite 默认不支持并发写，且外键约束默认是关的（`ondelete="CASCADE"` 可能不生效）；
2. MySQL 的 `utf8` 是残缺实现，连接串必须带 `charset=utf8mb4`，否则中文 emoji 存不进去。

**不这么做会怎样**：开发机上为了跑项目先装 MySQL、配账号、导数据，劝退一半新人。

## 8. 为什么建表放在 lifespan 里，而且生产建议改用 Alembic

**决策**：`Base.metadata.create_all()` 在应用启动钩子里执行，由 `AUTO_CREATE_TABLES` 控制。

**理由**：
- 放在 lifespan 而不是模块顶层，避免"导入模块就有副作用"，测试才干净。
- 开发阶段 `create_all` 足够：表不存在就建，已存在就跳过。

**它的局限（一定要能讲出来）**：
`create_all` 只会**新建**表，不会修改已存在的表。
你给 `Shot` 加了一个字段，它不会帮你加列，线上就等着报 `Unknown column` 吧。
所以生产必须用 **Alembic** 做版本化迁移：每次结构变更生成一个迁移脚本，
可以 review、可以回滚、可以在发布时按顺序执行。

**下一步任务**：引入 Alembic，并把生产的 `AUTO_CREATE_TABLES` 设为 `false`。

## 9. 为什么强调 N+1 查询和 selectinload

**决策**：关系默认懒加载，需要的地方显式 `selectinload`。

**理由**：
- N+1 是后端最典型的性能事故：查 20 部短剧，如果响应里要用到每部的剧集，
  就会额外发 20 条 SQL，接口从 20ms 变成 400ms，数据量一大直接拖垮数据库。
- 反过来，把关系设成全量 eager load 也不好：列表接口根本不需要关联数据，
  却每次都白查一张表。**所以显式声明、按需加载**才是可控的做法。

**怎么发现**：打开 SQLAlchemy 的 `echo=True`，或看 MySQL 慢查询日志，数一数一次请求发了几条 SQL。

## 10. Docker 和 Nginx 各自解决什么问题

**Docker 解决"环境不一致"**：
- "在我电脑上能跑"的根因是依赖版本、系统库、Python 版本不同；
- 镜像把这些全部打包固化，测试环境和生产环境跑的是同一个东西；
- `docker compose up` 一条命令起 API + MySQL + Nginx，新人不用看部署文档。

**Nginx 解决"公网入口该做的事"**：
- 反向代理：只暴露 80/443，应用端口不出公网，减少攻击面；
- TLS 终止：HTTPS 证书只在 Nginx 配一次，后端只管明文 HTTP；
- 慢请求超时控制：大模型生成要几十秒，Nginx 默认 60s 会 504，必须显式调大；
- gzip 压缩、限流、静态文件托管，这些都不该写进 Python 代码。

**为什么 api 用 `expose` 而不是 `ports`**：
`expose` 只在容器网络内可见，外界必须经 Nginx 才能访问 API——
这是"默认拒绝"的安全姿势。

## 11. 已知的未完成项 / 待优化清单（诚实清单）

一个负责任的 README 应该写清"哪里还不行"。这些也正是你下一步可以自己动手的部分：

| 项 | 现状 | 影响 |
|---|---|---|
| Docker / Nginx 实机验证 | 配置已写，开发机无 Docker | 首次 `docker compose up` 可能要调 |
| MySQL 生产路径 | 未验证（缺凭据） | 切库时注意 utf8mb4 和外键行为 |
| Alembic 迁移 | 未引入 | 生产改表结构会有风险 |
| 鉴权 | 无 | 任何人都能调接口，上线前必须加 JWT |
| 异步数据库驱动 | 用同步 PyMySQL + 异步路由 | 高并发下线程池会成为瓶颈，可换 asyncmy |
| AsyncClient 复用 | 每次调用新建 httpx 客户端 | 高频调用会浪费连接建立开销 |
| 生成任务同步等待 | 生成走同步请求 | 真实场景应改为后台任务 + 轮询/SSE 推送进度 |
| 限流与配额 | 无 | 大模型调用是真金白银，必须防止被刷 |

**最后一条特别重要**：接上真实大模型后，每一次生成都是钱。
上线前至少要有"每用户每日调用上限"，这是 AI 应用区别于传统 Web 应用的额外必修课。
